# Add voice search to your docs with a Managed Agent and client tools

A voice button on any documentation site, added with one `<script>` tag. A visitor asks a question out loud, and a Cartesia Managed Agent answers from your docs, names the page it used, and scrolls the page to that section. The agent runs `ink-2` for speech recognition, `sonic-3.6` for its voice and `gpt-4.1` as the LLM by default (set `AGENT_MODEL_ID` to pick another model from Cartesia's list). The widget is a framework-free web component. The server is Hono on Node with a JSON vector store.

This recipe covers the Cartesia parts: the client tools, the result size limit and the token route. To run the finished widget and server, follow the [`examples/docs-voice-widget`](../../../examples/docs-voice-widget/README.md) README.

The trick is two client tools. The agent calls `search_docs`, the browser asks your server, and the result goes back to the agent over the same WebSocket. Then the agent calls `show_source`, and the browser scrolls to the cited section. Nothing on Cartesia's side needs to reach your server.

## Prerequisites

- A Cartesia API key. An OpenAI API key is optional: with it, search uses `text-embedding-3-small` embeddings, and without it, a keyword (BM25) index
- Node 22.22 or newer
- The agent connection basics from [Connect to a Managed Agent from the browser](./01-talk-to-a-managed-agent.mdx)

On your own site, the embed is one line.

```html
<script src="https://your-server.example.com/widget.js" defer>
</script>
```

## Why search is a client tool and not a webhook tool

Cartesia only calls public HTTPS webhooks. A client tool runs in the connected browser, which can call any server it can reach, including `localhost`. So development needs no tunnel, and the search route lives next to the token route on the same Hono server.

## How do I give a Managed Agent client tools?

`scripts/agent-config.ts` defines both tools. `search_docs` expects a response and runs right away. `show_source` is fire and forget, so the agent keeps talking while the page scrolls.

```ts filename="scripts/agent-config.ts"
export const SEARCH_TOOL = {
  type: 'client',
  name: 'search_docs',
  description:
    'Searches this documentation site. Call it before answering any question about the product, with a short search query in English. Returns the best matching sections, each with a source_id.',
  pre_tool_speech: 'auto',
  execution_mode: 'immediate',
  expects_response: true,
  response_timeout_secs: 10,
  parameters: {
    type: 'object',
    properties: {
      query: { type: 'string', description: 'A short search query, for example "client tool result size limit".' },
    },
    required: ['query'],
  },
} as const;
```

`SOURCE_TOOL` has the same shape with `name: 'show_source'`, one required `source_id` string, `pre_tool_speech: 'off'`, `execution_mode: 'async'` and `expects_response: false`.

The prompt tells the agent when to call each one. It searches first, cites before it speaks, and answers only from the results.

```md filename="scripts/agent-config.ts"
# How to answer
Every answer about the product takes the same three steps, in this order, including follow-up questions on a topic you already covered:
1. Call search_docs with a short query.
2. Call show_source with the source_id of the result you rely on most. Prefer a result with on_this_page set to true when it answers the question.
3. Speak the answer, using only what the results say.

- Never skip step 2 when you answer from the results. Never mention it either: the page scrolls by itself, so do not say you are showing, opening or highlighting anything.
- If the results do not cover the question, skip show_source, say you could not find it in the docs and suggest a related topic they cover. Never guess at APIs, limits or values.
```

The setup script creates the two tools with `POST /v1/agents/tools`, then an agent that lists their ids in `tools`. It also ends idle calls after 60 seconds of silence (`inactivity_end_call_secs: 60`), which matters for a button any visitor can press.

## Handle client_tool_call in the browser

The service sends a `client_tool_call` event with `tool_call_id`, `tool_name`, `parameters` and `expects_response`. The vendored agents client in `widget/src/agents-web/` turns it into an event with a `respond` function. The web component forwards each call to a small dispatcher and answers only when there is something to send.

```ts filename="widget/src/element.ts"
    client.on('client_tool_call', async (call) => {
      if (this.client !== client) return;
      const out = await this.tools.run(call.toolName, call.parameters);
      if (out && this.client === client) call.respond(out.result, out.isError ? { isError: true, errorType: 'tool_failed' } : undefined);
    });
```

The `this.client !== client` checks drop calls from a session the visitor already ended, so a late search result never lands in the next session.

The dispatcher lives in `widget/src/tools.ts`. Tool names and parameters there must match `scripts/agent-config.ts`, since nothing checks them against each other. `search_docs` returns the server's `result` string as is and keeps the `sources` map for itself. `show_source` returns `null` because the agent does not wait for it.

```ts filename="widget/src/tools.ts"
  async run(name: string, params: Record<string, unknown>): Promise<{ result: string; isError?: boolean } | null> {
    if (name === 'search_docs') {
      const query = typeof params.query === 'string' ? params.query : '';
      if (!query.trim()) return { result: 'Pass a query.', isError: true };
      this.host.onSearching(true);
      try {
        const { result, sources } = await this.host.search(query);
        for (const [id, s] of Object.entries(sources)) this.known.set(id, s);
        return { result };
      } catch {
        return { result: 'Search is unavailable right now. Say you could not look it up.', isError: true };
      } finally {
        this.host.onSearching(false);
      }
    }
    if (name === 'show_source') {
      const id = typeof params.source_id === 'string' ? params.source_id : '';
      const source = this.known.get(id);
      if (source) this.host.cite(id, source);
      return null;
    }
    return { result: `Unknown tool ${name}.`, isError: true };
  }
```

An error result is a sentence the LLM can act on, not an exception. "Say you could not look it up" turns a failed fetch into a spoken apology instead of a guess.

`show_source` only looks up ids that a search in this session returned. The agent never sees a URL, so it cannot invent one, and a made-up `source_id` does nothing.

## Send client_tool_result under 4096 bytes

`respond` sends one `client_tool_result` event with the matching `tool_call_id`, the `result` string, and `is_error` plus `error_type` when set. It sends nothing when the agent did not ask for a response, and answers each call id once.

Results can be at most 4096 bytes. Per the Cartesia docs, a longer result is replaced with an error whose `error_type` is `result_too_large`, so the agent gets nothing useful. `truncateToolResult` cuts at `MAX_TOOL_RESULT_BYTES = 4096` as a last guard. Cutting JSON in the middle leaves it broken, though, so the server keeps the result well under the limit before it ever reaches the browser.

## Search the docs index on the server

`POST /api/search` takes the query and the visitor's current path. It embeds the query, ranks every section by cosine similarity (or by BM25 keyword score when the index was built without an OpenAI key), takes the top 50 candidates, adds a small boost to those on the page the visitor is reading, and keeps the top four. The boost is 3% of the best score, so it works on cosine and BM25 scales alike and only breaks near ties.

```ts filename="server/search.ts"
export function boostSamePage(
  ranked: Array<{ chunk: Chunk; score: number }>,
  page: string | undefined,
  k: number,
): Array<{ chunk: Chunk; score: number }> {
  if (ranked.length === 0) return [];
  const top = ranked.reduce((m, r) => (r.score > m ? r.score : m), -Infinity);
  const bump = SAME_PAGE_BOOST * Math.abs(top);
  return ranked
    .map((r) => ({ chunk: r.chunk, score: r.score + (samePage(r.chunk.url, page) ? bump : 0) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, k);
}

export async function searchDocs(
  index: DocIndex,
  embed: Embedder,
  query: string,
  page?: string,
): Promise<SearchResponse> {
  const q = query.trim().slice(0, MAX_QUERY_CHARS);
  if (!q || index.chunks.length === 0) return packResults([], page);
  if (index.model === KEYWORD_MODEL) {
    return packResults(boostSamePage(keywordSearch(index.chunks, q, CANDIDATES), page, TOP_K), page);
  }
  const [vector] = await embed([q]);
  return packResults(boostSamePage(index.search(vector!, CANDIDATES), page, TOP_K), page);
}
```

The index is one JSON file. Vectors are normalized when they are embedded, so a dot product is the cosine similarity, and a brute-force scan over a few thousand 512-dimension vectors is fast enough to skip a database.

`packResults` turns the top four sections into the tool result. Each item carries a `source_id`, the page and section names, an `on_this_page` flag and the text. The URL and anchor go into a separate `sources` map that only the widget sees. If the JSON is over 3,800 bytes, the loop shortens the longest text by a fifth, and drops the last result once every text is down to 80 characters.

The budget counts bytes with `TextEncoder`, not string length, so pages in Japanese or Hindi do not slip past it.

The template's ingest script splits each Markdown page into one section per heading, with a GitHub-style slug that becomes the anchor the widget scrolls to.

## Keep the API key on the server with a token route

The browser never sees `CARTESIA_API_KEY` or `OPENAI_API_KEY`. When the visitor presses Start talking, the widget calls `POST /api/token`, and the server mints a token with only the `agent` grant that expires in 60 seconds. The route calls `client.accessToken.create({ grants: { agent: true }, expires_in: 60 })`, and the widget uses the token once, to open `wss://api.cartesia.ai/v1/agents/websocket/{agent_id}`.

A public button that starts paid voice calls will get abused, so the route checks the `Origin` header against `ALLOWED_ORIGINS`, rate limits per IP, and never passes upstream errors to the browser.

```ts filename="server/app.ts"
  app.post('/api/token', async (c) => {
    if (!allowed(c)) return c.json({ error: 'This site is not allowed to start voice sessions.' }, 403, NO_STORE);
    if (!config.agentId) return c.json({ error: 'The voice agent is not set up yet.' }, 503, NO_STORE);
    const retry = tokenLimiter.take(deps.clientIp(c));
    if (retry) return c.json({ error: 'Too many sessions. Try again in a minute.' }, 429, { ...NO_STORE, 'Retry-After': String(retry) });
    try {
      const { token, expiresIn } = await deps.mintToken();
      return c.json({ token, expiresIn, agentId: config.agentId }, 200, NO_STORE);
    } catch {
      return c.json({ error: 'Could not start a voice session.' }, 502, NO_STORE);
    }
  });
```

The limits are 4 tokens a minute and 30 an hour per IP, and 30 searches a minute. A script can send any `Origin` header, so the origin check only stops other websites from embedding your widget. The rate limit is what slows scripts down. It lives in memory, which covers one process. Move it to Redis or your edge if you run more than one.

On a site with a Content Security Policy, allow `connect-src wss://api.cartesia.ai https://your-server.example.com` and `worker-src blob:`.

## Scroll to the cited section

When the agent cites a section on the current page, the widget finds the heading by its anchor id, scrolls to it, and draws a tinted box over the heading and everything up to the next heading of the same level. The box is positioned in the page, so the host's own CSS is never touched. Sources on other pages stay as chips in the panel, because following a link reloads the page and ends the call.

Models sometimes answer without calling `show_source`. Once the assistant's transcript passes 40 characters with no citation, the widget waits 1.2 seconds and cites the top search result itself.

## Limits

The tool loop depends on the model calling `search_docs` before it answers. The prompt asks for that, but a model can still answer from memory, so check answers against your docs before you put the widget on a public site.
